\section*{Einleitung}

Im Rahmen der Projektarbeit im Fach "Software Engineering" bestand die Aufgabe darin, ein spezifisches Teilmodul eines größeren Softwaresystems eigenständig zu konzipieren und zu implementieren. Dabei lag der Fokus auf der vollständigen Durchführung aller wesentlichen Phasen des Softwareentwicklungsprozesses – von der Anforderungserhebung über Architektur und Design bis hin zur Umsetzung und Testung.

Das individuelle Thema dieser Arbeit war die Entwicklung einer Steuerung zur Temperaturregelung eines Backofens. Ziel war es, ein System zu entwerfen, das dem Benutzer die Auswahl verschiedener Heizmodi sowie eine präzise Temperatureinstellung ermöglicht und dabei sicherheitsrelevante Aspekte berücksichtigt. Die Steuerung sollte außerdem hardwareunabhängig simuliert und auf einem Standard-PC lauffähig umgesetzt werden. Als Benutzerschnittstelle standen zwei simulierte Drehregler (für Temperatur und Modus) sowie ein Display zur Anzeige von Temperatur, Status und Warnhinweisen zur Verfügung.

Die Umsetzung folgte einem iterativen Vorgehensmodell mit vier funktional abgeschlossenen Entwicklungszyklen. Nach jeder Iteration wurde eine lauffähige Version des Systems bereitgestellt, um schrittweise Funktionalität, Sicherheit und Benutzerfreundlichkeit zu erweitern. Im Verlauf des Projekts wurde besonderer Wert auf Modularität, Wiederverwendbarkeit, Nachvollziehbarkeit der Anforderungen und eine klare Trennung von Verantwortlichkeiten gelegt.

Diese Dokumentation beschreibt im Folgenden die eingesetzten Technologien, die gewählte Architektur, das Softwaredesign, die umgesetzten Anforderungen sowie die einzelnen Iterationen inklusive ihrer Ergebnisse und Testabdeckungen.

\section{Annahmen über das System}

Die nachfolgenden Anforderungen basieren auf spezifischen Annahmen über die Systemumgebung und verfügbare Hardwarekomponenten. Diese Annahmen bilden die Grundlage für das Design, die Funktionalität und die Umsetzung der Steuerung:

\begin{itemize}
    \item \textbf{Display:}  
    Das System verfügt über ein integriertes Display, das folgende Informationen darstellen kann:
    \begin{itemize}
        \item Aktuelle Temperatur im Garraum
        \item Symbol zur Anzeige des Vorheizstatus
        \item Uhrzeit bzw. verbleibende Laufzeit eines Timers
        \item Warnhinweis bei automatischer Abschaltung
    \end{itemize}

    \item \textbf{Bedienelemente:}  
    Die Steuerung erfolgt über zwei physische Drehregler:
    \begin{itemize}
        \item Ein Regler zur Auswahl des Heizmodus (Betriebsart)
        \item Ein Regler zur Temperatureinstellung mit Einrastfunktion zur sicheren Moduswahl
    \end{itemize}

    \item \textbf{Heizelemente:}  
    Der Backofen besitzt drei unabhängig ansteuerbare Heizaggregate:
    \begin{itemize}
        \item Oberer Heizkörper
        \item Unterer Heizkörper
        \item Ringheizkörper an der Rückseite
    \end{itemize}

    \item \textbf{Lüftung:}  
    Ein Ventilator an der Rückwand kann separat ein- oder ausgeschaltet werden.

    \item \textbf{Sensorik:}  
    \begin{itemize}
        \item Ein Türkontaktsensor erkennt, ob die Backofentür geöffnet oder geschlossen ist.
        \item Ein Temperaturfühler misst kontinuierlich die aktuelle Garraumtemperatur.
    \end{itemize}

    \item \textbf{Schaltverhalten:}  
    Sämtliche Heizaggregate und der Ventilator lassen sich ausschließlich binär (Ein/Aus) steuern.
\end{itemize}

\section{Requirements Engineering}

\subsection{Funktionale Anforderungen}

\begin{enumerate}[label=\textbf{R-1.\arabic*}, ref=R-1.\arabic*, itemsep=0pt, topsep=0pt, font=\bfseries]
    \item \label{req:1.1} Das System muss es dem Benutzer ermöglichen, die Temperatur über einen Drehregler einzustellen.
    \item \label{req:1.2} Das System muss Temperatureinstellungen in 1\,\textdegree{}C-Schritten zulassen.
    \item \label{req:1.3} Das System muss Temperatureinstellungen im Bereich von 50\,\textdegree{}C bis 300\,\textdegree{}C unterstützen.
    \item \label{req:1.4} Das System muss dem Benutzer erlauben, eine Betriebsart über einen separaten Drehregler auszuwählen.
    \item \label{req:1.5} Folgende Betriebsmodi müssen wählbar sein:
    \begin{itemize}
        \item Ober-/Unterhitze
        \item Oberhitze
        \item Unterhitze
        \item Grillfunktion
        \item Umluft
        \item Heißluft
    \end{itemize}
    \item \label{req:1.6} Das System muss die Heizaggregate entsprechend der gewählten Betriebsart automatisch aktivieren:
    \begin{itemize}
        \item Ober-/Unterhitze: Oberer und unterer Heizkörper
        \item Oberhitze: Oberer Heizkörper
        \item Unterhitze: Unterer Heizkörper
        \item Grillfunktion: Oberer Heizkörper
        \item Umluft: Oberer und unterer Heizkörper + Ventilator
        \item Heißluft: Ringheizkörper hinten + Ventilator
    \end{itemize}
    \item \label{req:1.7} Das System muss die Heizaggregate einzeln ansteuern können.
    \item \label{req:1.8} Das System muss die Temperaturregelung mit einer Abtastrate von mindestens 1\,Hz durchführen.
    \item \label{req:1.9} Das System muss alle Heizaggregate deaktivieren, wenn die aktuelle Temperatur gleich oder größer der Solltemperatur ist.
    \item \label{req:1.10} Das System muss die gemäß Betriebsart definierten Heizaggregate aktivieren, wenn die aktuelle Temperatur unterhalb der Solltemperatur liegt.
    \item \label{req:1.11} Im Grillmodus muss das System die eingestellte Temperatur intern in vier Grillstufen umwandeln:
    \begin{itemize}
        \item Stufe 1: 240\,\textdegree{}C
        \item Stufe 2: 260\,\textdegree{}C
        \item Stufe 3: 280\,\textdegree{}C
        \item Stufe 4: 300\,\textdegree{}C
    \end{itemize}
    \item \label{req:1.12} Das System muss dem Benutzer folgende Informationen über ein Display anzeigen:
    \begin{itemize}
        \item Aktuelle Temperatur im Garraum
        \item Vorheizstatus (z.\,B. Symbol, wenn Solltemperatur erreicht)
        \item Restzeit eines eingestellten Timers
        \item Warnung bei automatischer Abschaltung
    \end{itemize}
\end{enumerate}

\subsection{Sicherheitsanforderungen}

\begin{enumerate}[label=\textbf{R-2.\arabic*}, ref=R-2.\arabic*, itemsep=0pt, topsep=0pt, font=\bfseries]
    \item \label{req:2.1} Das System muss den Heizbetrieb automatisch abschalten, wenn die Temperatur 320\,\textdegree{}C überschreitet.
    \item \label{req:2.2} Das System darf nicht weiter Heizen, wenn die Backofentür geöffnet ist.
    \item \label{req:2.3} Das System muss eine Fehlfunktion eines Heizaggregats erkennen, wenn die Temperatur innerhalb von 10 Abtastzyklen um weniger als 1\,\textdegree{}C steigt. In diesem Fall muss eine Warnung ausgegeben oder der Fehler im Systemprotokoll erfasst werden.
\end{enumerate}

\subsection{Nicht-funktionale Anforderungen}

    \item \label{req:3.2} Das Display muss Statusänderungen innerhalb von maximal 1 Sekunde anzeigen.
    \item \label{req:3.3} Das System muss alle sicherheitsrelevanten Zustandsänderungen und Fehlerereignisse mit Zeitstempel in der Konsole ausgeben.

\section{Softwarearchitektur}

In diesem Kapitel werden alle zentralen Module des Systems beschrieben und ihre jeweilige Funktion erläutert. Die strukturellen Abhängigkeiten zwischen den Modulen sind in Abbildung~\ref{fig:moduluebersicht} dargestellt.

Das Architekturkonzept verfolgt das Ziel, sämtliche Systemaufgaben in klar abgegrenzte Module zu unterteilen. Dabei werden alle Hardwarekomponenten (z.\,B. Sensoren, Heizkörper) sowie übertragene Daten in separaten Klassen gekapselt. Dies unterstützt eine saubere Trennung der Verantwortlichkeiten und erleichtert die Wartung und Erweiterung des Systems. Zentrale Datenstrukturen werden im Modul \texttt{GlobalModels} definiert und systemweit verwendet. Zusätzlich wird ein dediziertes \texttt{LoggingModule} eingesetzt, um alle Protokollierungsaufgaben vom Anwendungscode zu trennen.

\subsection*{Main}
Das Modul \texttt{Main} dient als Einstiegspunkt des Programms. Es initialisiert alle notwendigen Komponenten und erstellt eine Instanz des zentralen Steuerungsmoduls \texttt{OvenController}.

\subsection*{OvenControllerModule}
Der \texttt{OvenController} stellt die zentrale Steuereinheit des Systems dar. Er koordiniert die Funktionsmodule innerhalb einer fortlaufenden Hauptschleife. Zu seinen Aufgaben zählen:
\begin{itemize}
    \item Erfassen der Benutzereingaben über das \texttt{InputHandlerModule}
    \item Weitergabe der Eingaben an das \texttt{ModeControlModule} zur Interpretation
    \item Ausgabe von Informationen über das \texttt{OutputHandlerModule}
    \item Start und Überwachung des \texttt{SafetyModule} in einem separaten Thread
\end{itemize}
Die Ablauflogik der Steuerungsschleife ist in Abbildung~\ref{fig:controllloop} dargestellt.

\subsection*{SafetyModule}
Das \texttt{SafetyModule} führt kontinuierlich Sicherheitsüberprüfungen durch und läuft unabhängig vom Hauptprozess in einem eigenen Thread. Dadurch werden kritische Systemzustände (z.\,B. Überhitzung oder geöffnete Tür) frühzeitig erkannt und entsprechende Maßnahmen eingeleitet.

\subsection*{InputHandlerModule}
Dieses Modul verarbeitet alle Benutzereingaben. Es liest die Einstellungen der beiden Drehregler (Temperatur und Betriebsmodus) sowie den Timerwert aus. Die gesammelten Eingaben werden als strukturierte Objekte an den \texttt{OvenController} übergeben.

\subsection*{ModeControlModule}
Das \texttt{ModeControlModule} interpretiert die übergebenen Eingaben und entscheidet, welche Heizaggregate in Abhängigkeit vom gewählten Modus aktiviert werden sollen. Die konkrete Steuerung erfolgt über das \texttt{ThermalControlModule}.

\subsection*{ThermalControlModule}
Dieses Modul enthält die Ansteuerlogik für alle Heizaggregate und den Ventilator. Es stellt die direkte Schnittstelle zur (simulierten) Hardware dar und aktiviert oder deaktiviert Komponenten gemäß den Anforderungen des \texttt{ModeControlModule}.

\subsection*{OutputHandlerModule}
Das \texttt{OutputHandlerModule} ist für die Darstellung aller relevanten Informationen auf dem Display zuständig. Dies umfasst:
\begin{itemize}
    \item Aktuelle Temperatur im Garraum
    \item Gewählter Betriebsmodus
    \item Timerstatus
    \item Warnmeldungen und Sicherheitsanzeigen
\end{itemize}

\subsection*{SensorModule}
Das \texttt{SensorModule} kapselt die simulierten Sensoren des Systems. Dazu gehören:
\begin{itemize}
    \item \texttt{TemperatureSensor}: misst die aktuelle Temperatur im Garraum
    \item \texttt{DoorSensor}: erkennt den Zustand der Backofentür (offen/geschlossen)
\end{itemize}

\subsection*{GlobalModels}
Im Modul \texttt{GlobalModels} sind alle zentralen Datenstrukturen definiert, die zur intermodularen Kommunikation und Zustandshaltung benötigt werden:
\begin{itemize}
    \item \texttt{InputValues}: enthält Temperatur, Modus und Timerdaten
    \item \texttt{CookingMode}: beschreibt alle verfügbaren Betriebsmodi
    \item \texttt{OvenState}: bildet den aktuellen Zustand des Systems ab (z.\,B. \texttt{Idle}, \texttt{Preheating}, \texttt{Active})
\end{itemize}

\subsection*{LoggingModule}
Das \texttt{LoggingModule} ist für die zentrale Protokollierung aller sicherheitsrelevanten Ereignisse und Statusänderungen verantwortlich. Alle Module können dieses zur Ausgabe strukturierter Logeinträge mit Zeitstempel nutzen.

\section{Software Design}

Im Folgenden wird das Design der zentralen Module des Backofensystems beschrieben. Jedes Modul übernimmt eine klar definierte Aufgabe und orientiert sich an bewährten Software-Designprinzipien, insbesondere dem \textit{Strategy Pattern}, \textit{State Pattern} sowie der strikten Trennung zwischen Sensorik, Steuerung und Darstellung.

\subsection*{Designziele}

Das Software-Design verfolgt folgende Hauptziele:

\begin{itemize}
    \item \textbf{Erweiterbarkeit:}  
    Neue Betriebsmodi, Funktionen oder Anzeigeelemente sollen mit minimalem Änderungsaufwand integrierbar sein. Dies wird durch konsequente Modularisierung und lose Kopplung erreicht.

    \item \textbf{Beherrschbare Komplexität:}  
    Durch den Einsatz etablierter Entwurfsmuster – wie dem \textit{Strategy Pattern} für Regelalgorithmen und dem \textit{State Pattern} für Zustandsverwaltung – wird die Systemlogik übersichtlich und nachvollziehbar strukturiert.

    \item \textbf{Klare Verantwortungstrennung:}  
    Die Architektur folgt einem Schichtenmodell mit den Bereichen \textit{Sensorik} (Datenerfassung), \textit{Steuerung} (Verarbeitung und Logik) und \textit{Darstellung} (Benutzerausgabe). Jede Schicht ist funktional abgegrenzt, was Wartbarkeit und Erweiterbarkeit fördert.

    \item \textbf{Clean Code:}  
    Der Quellcode ist klar strukturiert, konsistent dokumentiert und folgt gängigen Namenskonventionen. Das unterstützt die langfristige Pflege des Systems.

    \item \textbf{Trennung von Produktivcode und Logging:}  
    Logging-Mechanismen sind vom Anwendungscode entkoppelt und in einem eigenen Modul gekapselt. Dadurch bleibt die Steuerlogik schlank und frei von Nebenfunktionen.

    \item \textbf{Testbarkeit:}  
    Die lose Kopplung und klar definierten Schnittstellen zwischen Modulen erleichtern Unit-Tests. Durch die konsequente Entkopplung lassen sich Komponenten isoliert validieren.
\end{itemize}

Diese Designprinzipien stellen sicher, dass das System nicht nur funktional robust ist, sondern auch langfristig wartbar und flexibel weiterentwickelt werden kann.

\newpage

\subsection*{GlobalModels}

Das Modul \texttt{GlobalModels} definiert zentrale Datenstrukturen und Enumerationen, die als gemeinsame Kommunikationsschnittstelle zwischen den Modulen dienen. Die Übergabe von Informationen erfolgt über klar gekapselte Objekte, was die Erweiterbarkeit fördert und die Konsistenz der Datenhaltung sicherstellt.

Die Klasse \texttt{InputValues} aggregiert alle wesentlichen Eingaben des Benutzers:
\begin{itemize}
    \item die gewünschte Zieltemperatur (Typ: \texttt{double}),
    \item den gewählten Heizmodus (Typ: \texttt{CookingMode}),
    \item sowie die eingestellte Timerdauer (Typ: \texttt{TimeSpan}).
\end{itemize}

Ergänzend dazu enthält die Klasse \texttt{OutputValues} alle Informationen, die dem Benutzer auf dem Display angezeigt werden sollen:
\begin{itemize}
    \item die aktuelle Temperatur,
    \item ein Statusindikator zur Zieltemperatur,
    \item der aktuelle Timerstand,
    \item sowie ein Warnhinweis bei sicherheitsrelevanten Ereignissen.
\end{itemize}

Die Enumeration \texttt{CookingMode} beschreibt alle verfügbaren Heizmodi des Backofens, darunter z.\,B. \texttt{Grill}, \texttt{Umluft} oder \texttt{OberUnterhitze}.

Der Enum \texttt{OvenState} bildet die internen Zustände des Systems ab, darunter \texttt{Idle}, \texttt{Preheating}, \texttt{Active}, \texttt{Error} und \texttt{Off}.

\subsection*{OvenControllerModule}

Das \texttt{OvenControllerModule} ist das zentrale Steuerungsmodul des Systems. Es implementiert die Ablaufsteuerung mithilfe des \textit{State Pattern}, wobei der aktuelle Betriebszustand über eine Referenz auf ein entsprechendes Zustandsobjekt verwaltet wird.

In regelmäßigen Zyklen wird die Methode \texttt{Run()} aufgerufen. Innerhalb dieses Zyklus:
\begin{itemize}
    \item werden die aktuellen Benutzereingaben über das \texttt{InputHandlerModule} erfasst,
    \item an das \texttt{ModeControlModule} zur Heizlogik-Interpretation übergeben,
    \item und die resultierenden Informationen über das \texttt{OutputHandlerModule} auf dem Display ausgegeben.
\end{itemize}

Zusätzlich wird in jeder Iteration der \texttt{TemperatureSensor} aktualisiert, um das Verhalten eines realen Sensors zu simulieren.

Die Zustandsverwaltung erfolgt über folgende implementierte State-Klassen:
\begin{itemize}
    \item \texttt{IdleState} – Der Ofen ist inaktiv, sämtliche Heizungen sind deaktiviert.
    \item \texttt{PreHeatingState} – Der Ofen heizt aktiv auf die vorgegebene Zieltemperatur.
    \item \texttt{ActiveState} – Die Zieltemperatur ist erreicht und wird konstant gehalten.
    \item \texttt{ErrorState} – Es wurde ein sicherheitskritischer Zustand erkannt; alle Komponenten werden abgeschaltet. Rückkehr in einen anderen Zustand ist ausgeschlossen.
    \item \texttt{OffState} – Der Ofen wurde manuell oder durch Ablauf des Timers deaktiviert.
\end{itemize}

Das Modul reagiert asynchron auf Sicherheitsereignisse: Das \texttt{SafetyModule} kann den Controller unmittelbar in den \texttt{ErrorState} versetzen, um eine sofortige Abschaltung bei Gefährdung sicherzustellen.

\subsection*{SafetyModule}

Das \texttt{SafetyModule} ist vollständig vom übrigen System entkoppelt und wird in einem separaten Thread ausgeführt. Es überwacht kontinuierlich sicherheitsrelevante Systemzustände und reagiert im Fehlerfall unverzüglich.

Die zentrale Klasse \texttt{SafetyHandler} verwaltet eine Sammlung von Sicherheitsregeln. In festen Intervallen ruft sie deren \texttt{Check()}-Methoden auf. Bei einem Regelverstoß wird der \texttt{OvenController} unmittelbar benachrichtigt und in einen sicheren Zustand versetzt – entweder den \texttt{IdleState} oder \texttt{ErrorState}, je nach Schwere des Ereignisses.

Folgende Sicherheitsregeln sind aktuell implementiert:

\begin{itemize}
    \item \texttt{OverheatRule}: Detektiert eine kritische Überschreitung der maximal zulässigen Temperatur und führt zum Wechsel in den \texttt{ErrorState}.
    \item \texttt{DoorOpenRule}: Erkennt eine geöffnete Tür während des Heizbetriebs. In diesem Fall wird in den \texttt{IdleState} gewechselt.
    \item \texttt{HeaterFailureRule}: Identifiziert defekte Heizaggregate, wenn trotz aktivierter Heizung über mehrere Zyklen kein Temperaturanstieg festgestellt wird. Dies führt zum Übergang in den \texttt{ErrorState}.
\end{itemize}

Durch die eigenständige Ausführung ist das \texttt{SafetyModule} in der Lage, unabhängig von Verzögerungen im Hauptprozess zuverlässig zu arbeiten. Damit trägt es wesentlich zur Betriebssicherheit und Fehlertoleranz des Systems bei.

\subsection*{InputHandlerModule}

Das \texttt{InputHandlerModule} ist für die Erfassung manueller Benutzereingaben zuständig. Es verarbeitet ausschließlich physische Interaktionen, nicht jedoch automatische Sensordaten.

Konkret werden die Drehwinkel zweier Regler ausgelesen:
\begin{itemize}
    \item ein Regler zur Temperatureinstellung,
    \item ein Regler zur Auswahl des Betriebsmodus,
    \item sowie ein optionaler Timerwert.
\end{itemize}

Die Drehregler implementieren ein generisches Interface \texttt{IRotaryController<T>}, das unterschiedliche Rückgabetypen wie \texttt{int} (für Temperatur) oder \texttt{Enum} (für Moduswahl) unterstützt. Der aktuelle Winkel wird intern gespeichert und über die Methode \texttt{ReadInput()} in einen konkreten Wert übersetzt.

Die zentrale Klasse \texttt{InputHandler} bündelt alle Eingabewerte in einem Objekt vom Typ \texttt{InputValues}. Diese strukturierte Datenübergabe vereinfacht die Verarbeitung in nachgelagerten Modulen und unterstützt die Erweiterbarkeit.

Der Zugriff erfolgt über den \texttt{InputHandlerProxy}, der zusätzlich alle Eingaben protokolliert. Das zugrunde liegende Proxy-Pattern trennt dabei strikt zwischen Anwendungscode und Logging, wodurch die Hauptlogik schlank und wartbar bleibt.

\subsection*{ModeControlModule}

Das \texttt{ModeControlModule} implementiert die Heizlogik des Backofens nach dem \textit{Strategy Pattern}. Die zentrale Klasse \texttt{ModeControl} verwaltet eine Referenz auf die aktuell aktive Strategie (\texttt{IModeStrategy}), die zur Laufzeit anhand des ausgewählten \texttt{CookingMode} ausgetauscht werden kann.

Die gewählte Strategie wird vom \texttt{OvenController} aufgerufen, um die entsprechenden Heizaggregate zu steuern. Dabei gibt jede Strategie einen Boolean-Wert zurück, der angibt, ob sich das System aktuell im Aufheizprozess befindet. Diese Information ist für den Zustand der Statemachine im \texttt{OvenControllerModule} relevant.

Folgende Heizstrategien sind verfügbar:

\begin{itemize}
    \item \texttt{IdleMode}: keine Heizkomponenten aktiv (Standardzustand)
    \item \texttt{TopBottomHeatMode}: oberer und unterer Heizkörper aktiv
    \item \texttt{TopHeatMode}: nur oberer Heizkörper aktiv
    \item \texttt{BottomHeatMode}: nur unterer Heizkörper aktiv
    \item \texttt{GrillMode}: oberer Heizkörper aktiv, Zieltemperatur wird in Grillstufen übersetzt
    \item \texttt{CirculatingAirMode}: Ober- und Unterhitze kombiniert mit Ventilator
    \item \texttt{HotAirMode}: Ringheizkörper und Ventilator aktiv
\end{itemize}

Jede Strategie besitzt eine eigene Liste von \texttt{IThermalController}-Instanzen, über die die jeweiligen Heizkomponenten und der Ventilator gezielt angesteuert werden können. Der \texttt{GrillMode} bildet dabei eine Sonderform: Die eingestellte Zieltemperatur wird hier in definierte Grillstufen umgewandelt (z.\,B. 240–300\textdegree C).

Der Zugriff auf das Modul erfolgt über einen \texttt{ModeControlProxy}, der zusätzlich für die Protokollierung zuständig ist. Damit bleibt die Heizlogik vom Logging vollständig getrennt.

\subsection*{ThermalControlModule}

Das \texttt{ThermalControlModule} bildet die unterste Abstraktionsebene zur gezielten Ansteuerung der Heizkörper und des Ventilators. Jede Komponente ist als Singleton implementiert, um sicherzustellen, dass im System stets nur eine Instanz pro Aktor existiert.

Die beteiligten Klassen implementieren zwei zentrale Schnittstellen:
\begin{itemize}
    \item \texttt{IThermalController} – zur Aktivierung und Deaktivierung der Komponente (Ein/Aus),
    \item \texttt{ITemperatureSource} – zur Bereitstellung von Temperaturwerten (sofern relevant).
\end{itemize}

Die Steuerung der Komponenten erfolgt ausschließlich durch Strategien im \texttt{ModeControlModule}, wodurch eine klare Trennung zwischen Logik und Ausführung gewährleistet ist.

Die folgenden Komponenten sind im Modul enthalten:

\begin{itemize}
    \item \texttt{TopHeater} – oberer Heizkörper,
    \item \texttt{BottomHeater} – unterer Heizkörper,
    \item \texttt{RearHeater} – Ringheizkörper an der Rückseite,
    \item \texttt{Ventilator} – Umluftventilator.
\end{itemize}

Da die Steuerungslogik vollständig in den jeweiligen Strategien gekapselt ist, bleibt das \texttt{ThermalControlModule} selbst zustandslos, wartungsarm und gut testbar.

\section{Geplante Implementierungsiterationen}

Die Implementierung des Backofensystems erfolgt schrittweise in mehreren aufeinander aufbauenden Iterationen. Jede Iteration verfolgt ein klar abgegrenztes Entwicklungsziel und liefert eine lauffähige Teillösung. Auf diese Weise entsteht schrittweise eine modular aufgebaute und testbare Steuerungssoftware.

\subsection*{Iteration 1: Grundstruktur und Kernfunktionalität}

In der ersten Iteration wird das Grundgerüst des Systems aufgebaut. Ziel ist es, eine erste funktionsfähige Version der Steuerung mit Temperaturregelung zu realisieren:

\begin{itemize}
    \item Implementierung des \texttt{Main}-Moduls zur Initialisierung des Gesamtsystems.
    \item Erstellung der zentralen Datenklassen \texttt{InputValues} und \texttt{OutputValues} im \texttt{GlobalModels}-Modul.
    \item Umsetzung des \texttt{OvenControllerModule} mit einem initialen \texttt{ActiveState} zur Steuerung der Temperatur.
    \item Vollständige Implementierung des \texttt{InputHandlerModule} und \texttt{OutputHandlerModule} zur Benutzerschnittstelle.
    \item Erste Heizlogik im \texttt{ModeControlModule} mit Standardstrategie, die alle Heizaggregate aktiviert.
    \item Implementierung des \texttt{ThermalControlModule} mit allen Aktoren (Heizelemente und Ventilator).
    \item Umsetzung des \texttt{SensorModule} mit \texttt{TemperatureSensor} und \texttt{DoorSensor}.
\end{itemize}

\subsection*{Iteration 2: Logging und Architekturstrukturierung}

In dieser Iteration wird die Protokollierung eingeführt, um Systemereignisse nachvollziehbar zu dokumentieren:

\begin{itemize}
    \item Entwicklung des zentralen \texttt{LoggingModule} mit Singleton-Loggerstruktur.
    \item Einführung von Proxy-Klassen für das \texttt{InputHandlerModule} und \texttt{ModeControlModule}, um Logging vom Produktivcode zu entkoppeln.
    \item Strukturverbesserungen zur Vorbereitung auf erweiterte Funktionalitäten.
\end{itemize}

\subsection*{Iteration 3: Zustandslogik und Heizstrategien}

In der dritten Iteration wird die vollständige Zustandsmaschine implementiert. Die Heizlogik wird um alle Betriebsmodi ergänzt:

\begin{itemize}
    \item Erweiterung des \texttt{OvenControllerModule} um die Zustände \texttt{IdleState}, \texttt{PreHeatingState}, \texttt{ErrorState} und \texttt{OffState}.
    \item Umsetzung aller im System definierten Heizstrategien im \texttt{ModeControlModule}.
    \item Erweiterung der Proxy-Mechanismen für Zustandsübergänge (z.\,B. Logging bei Zustandswechseln).
\end{itemize}

\subsection*{Iteration 4: Sicherheitslogik und Timer}

Die finale Iteration fokussiert sich auf die Absicherung des Systems durch Echtzeitüberwachung:

\begin{itemize}
    \item Implementierung des \texttt{SafetyModule} als paralleler Thread mit zyklischer Regelprüfung.
    \item Umsetzung der Sicherheitsregeln:
    \begin{itemize}
        \item \texttt{OverheatRule}: Überhitzungsschutz,
        \item \texttt{DoorOpenRule}: Türkontrolle bei Heizbetrieb,
        \item \texttt{HeaterFailureRule}: Erkennung fehlerhafter Heizaggregate.
    \end{itemize}
    \item Ergänzung eines Timer-Features, das vom Benutzer gesetzt werden kann und die Restlaufzeit im Display anzeigt.
\end{itemize}

\subsection{Abweichungen vom Feinentwurf}

Während der Umsetzung wurden folgende Anpassungen gegenüber dem ursprünglichen Design vorgenommen:

\begin{itemize}
    \item Einführung einer eigenen Proxy-Klasse für die Statemachine im \texttt{OvenControllerModule}, um Zustandsübergänge zu protokollieren. Dadurch entfiel die Logging-Logik im Controller selbst.
    \item Verzicht auf die ursprünglich geplante Enum-Klasse \texttt{OvenState}; der aktuelle Zustand wird stattdessen direkt über das aktive State-Objekt verwaltet.
    \item Zustandswechsel wurden in die Methode \texttt{CheckStateTransition()} innerhalb des Interfaces \texttt{IState} ausgelagert.
    \item States erhielten Zugriff auf notwendige Instanzvariablen zur Umsetzung ihres Verhaltens.
    \item Der \texttt{OffState} wurde verworfen, da seine Funktionalität durch bestehende States ausreichend abgedeckt ist.
    \item Einführung einer abstrakten Basisklasse \texttt{BaseModeStrategy} im \texttt{ModeControlModule}, um wiederkehrende Logik zwischen den Heizstrategien zu kapseln. Diese verwaltet auch die zugehörigen \texttt{IThermalController}-Instanzen.
\end{itemize}

\subsection{Abweichungen vom Feinentwurf}

Während der Umsetzung wurden folgende Abweichungen gegenüber dem initialen Entwurf vorgenommen:

\begin{itemize}
    \item \textbf{Kein automatisches Ausschalten über Timer:} Auf eine automatische Deaktivierung nach Ablauf des Timers wurde verzichtet. In der Praxis würde dies entweder einen motorisierten Regler erfordern oder zu inkonsistentem Systemverhalten führen. Die Timerfunktion dient ausschließlich der Anzeige.
    
    \item \textbf{Proxy-Klasse für Sicherheitsregeln:} Zur Trennung von Logging und Prüflogik wurde eine zusätzliche Proxy-Klasse für das \texttt{SafetyModule} eingeführt.
    
    \item \textbf{HeaterFailureRule:} Die Temperaturhistorie wird nun als \texttt{int}-Array anstelle von \texttt{double} gespeichert, da für die Regelung eine Ganzzahldarstellung ausreicht und Rechengenauigkeit nicht erforderlich ist.
    
    \item \textbf{OvenController-Zugriff:} Der \texttt{OvenController} wurde um eine Methode zur Abfrage des aktuellen Zustands erweitert. Ebenso wurde der entsprechende Zugriff im \texttt{StateProxy} implementiert.
\end{itemize}
